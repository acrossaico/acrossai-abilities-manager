# SECURITY REVIEW REPORT — STAGED CHANGES

## Executive Summary

**No new vulnerabilities are introduced by the staged changeset.** All four findings are
informational: three are previously-tracked constraints whose mitigations were re-verified as present
in the staged code, and one records a residual risk inherent to the feature rather than to a defect.

The changeset's security character is unusual and worth stating plainly: it **removes** an access
mechanism (the registration gate) and replaces it with an existing one (per-ability `site_allowed`).
The enforcement path itself — `AcrossAI_Ability_Override_Processor` at `wp_abilities_api_init`
P100001 — is **not in the staged diff** and is unchanged, so the question is not whether enforcement
works but whether the one-time translation faithfully carries the old configuration into it. That is
covered by SEC-102-4 below.

Two things improved: SEC-003 gained an unconditional capability floor it did not previously have, and
the retired `acrossai-abilities-library/v1` REST namespace (a `manage_options` write surface) is
deleted outright, reducing attack surface.

## Vulnerability Findings

### [INFORMATIONAL] SEC-102-1 — Privileged migration runs unauthenticated on every request

**Location:** `includes/Main.php:471`, `includes/Modules/Abilities/AcrossAI_Library_Gate_Migration.php`
**OWASP Category:** A01:2025-Broken Access Control · **CWE-862: Missing Authorization**
**CVSS:** 0.0 (accepted design, mitigations verified)

The translation is wired to `init` priority 100 — an all-paths hook — with no capability or nonce
check. This is deliberate and pre-agreed (tracked as **SEC-009**): the exposure it closes is reachable
via REST and MCP, so an `admin_init` trigger could never reach a site whose only traffic is API
traffic. Restricting the trigger would reintroduce **SEC-001**.

Mitigations re-verified as present in the staged code:
- **Reads no request input.** `grep` for `$_GET|$_POST|$_REQUEST|current_user_can|wp_verify_nonce`
  in the migration returns nothing, and `Test_Library_Gate_Migration_No_Request_Input` enforces this
  with a comment-stripped token scan (5 tests, CI-gated).
- **Atomic claim.** `add_option( DONE_OPTION, '1', '', false )` is a single INSERT that fails when the
  row exists, so concurrent requests cannot both translate (SEC-008).
- **Idempotent**, and **fail-safe on an empty registry** — it releases the flag rather than translating
  nothing and deleting the source option.

**Remediation:** None. Documented decision; mitigations verified.
**Spec-Kit Task:** TASK-SEC-009 (closed)

### [INFORMATIONAL] SEC-102-2 — Redirect fires for unauthorized users

**Location:** `admin/Partials/Integrations_Redirect.php`, `includes/Main.php:325-326`
**OWASP Category:** A01:2025-Broken Access Control · **CWE-601: Open Redirect** (evaluated, not present)
**CVSS:** 0.0

Hooked to `admin_page_access_denied`, which by definition fires *after* WordPress has decided the
visitor may not see the page. Three properties checked:

- **Not an open redirect.** The destination is always rebuilt from `admin_url()`; only a
  `sanitize_key()`-ed `tab` is appended. Verified by test: a `tab` of `https://evil.example/?x=` cannot
  place a host or `//` in the target.
- **No redirect loop.** `redirect_target()` returns `null` for every slug except the retired one, so
  the abilities page's own denial does not bounce again.
- **No privilege change and no disclosure.** It relocates an unauthorized visitor to another page that
  will also deny them.

Also hardened during review: `sanitize_key()` is typed `string`, so `?page[]=x` raised a `TypeError` on
an `admin_init`-priority hook — a fatal on an arbitrary admin request. Non-scalars are now discarded
before they reach it.

**Remediation:** None required.
**Spec-Kit Task:** TASK-SEC-102-2 (closed)

### [INFORMATIONAL] SEC-102-3 — Relocated capability check, now with a floor (SEC-003 improved)

**Location:** `admin/Partials/Integrations_Settings_Menu.php` (`CAPABILITY_FLOOR`, `sanitize_option()`)
**OWASP Category:** A01:2025-Broken Access Control · **CWE-1188: Insecure Default**
**CVSS:** 0.0 (strengthened relative to the pre-change state)

SEC-003 warned that `acrossai_integration_toggle_capability` is only raise-only while the outer page
gate survives. The relocated save path now layers an **unconditional `manage_options` floor ahead of**
the single filtered check, per `PATTERN-FILTERABLE-CAPABILITY-RAISE-ONLY`. The floor matters because
`sanitize_option()` is a public `sanitize_option_{$option}` callback: any code writing the option
directly runs it without the Settings API page gate.

Verified by `Test_Integrations_Settings_Capability` (5 tests, CI-gated): a filter returning `read`
lets a subscriber neither enable **nor disable**; a filter returning `manage_network_options` still
blocks a plain administrator (raise-only intact); an empty filter value fails closed; an administrator
succeeds. Denials fire `acrossai_integration_toggle_denied` and surface via `add_settings_error()`.

**Remediation:** None. SEC-003 is resolved rather than mitigated.
**Spec-Kit Task:** TASK-SEC-003 (closed)

### [INFORMATIONAL] SEC-102-4 — Residual: a skipped translation leaves previously-blocked abilities reachable

**Location:** `includes/Modules/Library/AcrossAI_Ability_Library_Processor.php:63-80`
**OWASP Category:** A04:2025-Insecure Design · **CWE-862**
**CVSS:** 0.0 (inherent to the accepted design)

Removing the gate means every first-party definition now registers unconditionally. On a site whose
operator had switched a category off, the only thing standing between that and wider exposure is the
one-time translation writing `site_allowed = false`. If it never runs, or runs against an empty
registry, those abilities become reachable with no notice and no log (spec clarifications Q1/Q2).

Verified controls: the fail-safe guard releases the done-flag when the definition set is empty; the
never-overwrite rule is now `is_already_decided()` with 7 CI-gated cases (it tests `site_allowed`
specifically, not row existence — treating any row as a shield would leave abilities reachable);
`Test_Library_Processor_No_Gate` (CI, mutation-verified) proves no gate can silently return.

**Remediation:** None available in code. Operators upgrading a site that used category gating should
confirm the expected count of Force Block overrides after upgrade (`quickstart.md` §2).
**Spec-Kit Task:** TASK-SEC-102-4 (accepted risk)

## Confirmed Secure Patterns

- **No raw SQL added.** The only `INSERT` token in the diff is inside a comment; all persistence goes
  through BerlinDB (`AcrossAI_Abilities_Query`).
- **No hardcoded secrets.** No credentials, keys or tokens in the diff.
- **Input sanitised at the boundary.** `tab_group` declares `'sanitize_callback' => 'sanitize_key'`;
  the redirect discards non-scalars then `sanitize_key()`s; `AcrossAI_Key_Sanitizer::key()` bounds
  every registry-boundary key to 100 chars after `sanitize_key()` (13 CI tests).
- **`slugs` is never request-supplied.** It is derived server-side from
  `AcrossAI_Ability_Group::member_names()` and consumed with a strict `in_array( …, true )` in-memory
  filter — no injection surface.
- **New REST route is gated.** `/abilities/toolsets` uses the orchestrator's shared
  `check_permission`, which enforces `manage_options` **and** `X-WP-Nonce`, and returns only
  `true|WP_Error`.
- **All output escaped with the most specific function.** `esc_attr()` for attributes, `esc_html()` for
  text, `checked()` for state; third-party-supplied `category_label` is `esc_html()`-escaped at render.
- **Attack surface reduced.** The entire `acrossai-abilities-library/v1` namespace — including a
  `manage_options` `POST /abilities/config` write endpoint — is deleted; verified returning
  `404 rest_no_route` on a live site.
- **Enforcement path untouched.** `AcrossAI_Ability_Override_Processor` is absent from the diff.

## Action Plan

1. **No blocking findings.** Nothing in the staged changeset requires remediation before commit.
2. **Post-upgrade verification (operational, not code)** — on any site that used category gating,
   confirm the Force Block count after upgrade per `quickstart.md` §2. This is the only control for
   SEC-102-4 and it cannot be automated: the source configuration is consumed and deleted.
3. **Follow-ups already filed and out of scope here**: #184 (abilities with no toolset), #185 (bulk
   action drops list parameters; per-page over 100 silently ignored). Neither is a security finding.
